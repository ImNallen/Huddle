# Agent instructions

`README.md` is for humans. Keep it short and about using and hosting Huddle. This file is for AI agents. Put agent-facing detail, such as test ports and suite internals, here instead of in the README. `CLAUDE.md` imports this file.

## Git and pull requests

Do not commit, push, or create a pull request until the user tells you to. Leave changes uncommitted in the working tree and report what changed.

## Verify a change

Run these from the repository root. Build before the UI suite, because it runs the production server.

```sh
pnpm typecheck
pnpm build
pnpm format:check
pnpm db:migrate
docker compose --profile dev up -d livekit-dev
pnpm test:integration
pnpm test:access
pnpm --filter @huddle/server test:rooms-migration
pnpm exec playwright install chromium
pnpm test:ui
cargo check --locked --manifest-path apps/desktop/src-tauri/Cargo.toml
```

On macOS, also build the app bundle with `pnpm --filter @huddle/desktop tauri build --bundles app`.

The integration, access, and UI suites each create a scratch database named `huddle_scratch_*` on the PostgreSQL server in `DATABASE_URL`, start their own server with a known `SETUP_CODE`, and drop the database afterwards. The `DATABASE_URL` user needs the `CREATEDB` privilege. Never point the suites at real user data.

The integration suite needs a real LiveKit, so start `livekit-dev` first. It publishes `LIVEKIT_PORT` (7880 by default) and `LIVEKIT_UDP_PORT` (7882 by default) on `127.0.0.1`, and `pnpm setup:local` claims both per checkout. The suite reads `LIVEKIT_API_SECRET`, plus `LIVEKIT_PUBLIC_URL` or `LIVEKIT_PORT`, from the environment and passes them to its server. If nothing answers, or the secret is missing, it fails with the start command before it creates a database. `tests/voice.spec.ts` and `tests/voice-access.spec.ts` need it the same way, and no other suite does. `.env` values never override the environment, so CI sets the secret and address to match its service container.

`pnpm dev` on 3000, 3002, 3003, and 1420 can keep running, because the suites use their own ports:

- The integration suite runs the production server on 3100 and 3101. It restarts the server to check persistence, and it starts a second server on 3102 and 3103 with `SOCKET_MAX_AGE_SECONDS=2` and no LiveKit secret. `TEST_PORT` changes the HTTP port, and the other ports follow it.
- `pnpm test:access` uses 3200 and 3201.
- The UI suite runs the desktop frontend on `127.0.0.1:1520` and, for each spec file, a production server on `localhost:3400` and `3401`. `HUDDLE_UI_DESKTOP_PORT` and `HUDDLE_UI_SERVER_PORT` change them.
- `test:serve` uses 3790 and 3791. Its target cannot use LiveKit's port, which is 8443 unless `LIVEKIT_PUBLIC_URL` says otherwise.

The server has no test mode. Suites send the headers Serve would add, from outside the process. `tailscale()` in `apps/server/scripts/harness.ts` is the one helper that knows those names. Node clients pass it to `fetch` and `ws`. Playwright sets it as `extraHTTPHeaders` on a browser context, with one context per person. Those headers trigger a preflight on a cross-origin fetch, which production CORS must refuse, so native-shell specs add a no-op `context.route` and Playwright answers the preflight. `pnpm dev` plays Serve with `runtime/dev-serve.ts`, and it refuses anything but a loopback HTTP `SERVER_URL`. `playwright.config.ts` turns off Chrome's local network prompt, because it would stop `tests/cross-site.spec.ts` requests before the server sees them.

Every data POST and `profile.save` must carry `X-Huddle-User`, or it answers 401. Only setup and join go without it, because no account exists yet. `Client` in the harness learns the ID from `stage()` and `act()`. A raw `fetch` in a test must send it, as `apiPost` in `tests/accounts.ts` does.

`pnpm typecheck` also runs `packages/ui/src/appearance/check.ts` in `@huddle/ui`. Its tables cover `parseColor`, `chat.css` agreeing with `TOKENS` in both directions, every contrast floor on Huddle and the built-in themes, a grid of 240 seeds chosen to break derivation, `appearance-boot.js` run in `node:vm` against stored states and an attack table with its CSS compared to `cssOf`, `parseThemeFile`, and the Open VSX helpers: `extensionPath` with a traversal table, `variantsOf`, and `pairVariants`. A stored theme's values can't reach a stylesheet without passing that boot regex or `parseColor`, so edit the two together.

`build.cssTarget` in both Vite configs is load-bearing. Below the `light-dark()` floor, Lightning CSS replaces `light-dark()` with a polyfill in the build only, which breaks swatches while `pnpm dev` still looks right. The swatch test in `tests/appearance.spec.ts` runs against the production server to catch this. The desktop half runs on Vite's dev server, so a change to the desktop's CSS target needs a look at `apps/desktop/dist`.

`test:rooms-migration` covers migrations 000, 006, 007, 011, 013, and 014. Same-named channels in different rooms survive, channels and stored `channel.created` events are backfilled to the `text` kind, and every insert must state a kind. It seeds logins, sessions, a watch ticket, a join code, photos, and direct messages at 012, then checks that 013 keeps every row and ID, leaves logins NULL, keeps old usernames as labels, drops credential tables, and issues a valid join code. A fresh install must reach the same shape as an upgrade. `000_better_auth_baseline.sql` was reconciled against a real `pg_dump --schema-only` of Better Auth's own migrator.

`pnpm test:integration` also runs `scripts/group-integration.ts` against a separate scratch database on 3300/3301 (`GROUP_TEST_PORT` changes the first port). CI runs every suite above except the native bundle and `test:serve`, uses Chrome on Ubuntu, PostgreSQL 17 and LiveKit as service containers to match `compose.yaml`, and compiles the desktop on macOS, Windows, and Linux. A `publish` job then runs on pushes to `main`, after the suites pass, and pushes the image that `deploy/update.sh` pulls.

`pnpm --filter @huddle/server test:serve <https address>` is a manual check against real `tailscale serve`, on a machine with a tailnet. CI has no tailnet, so rerun it on Tailscale upgrades. It also checks that Tailscale uses a TUN device, that the backend and LiveKit ports are closed on the node's Tailscale address, and that LiveKit accepts the server's token over `wss` on 8443. Userspace mode forwards a peer's direct connection onto loopback, past Serve, so `runtime/production.ts` refuses to start under it. The integration suite proves that refusal with a fake `tailscale` on `PATH`.

`deploy/update.sh` has no suite. Its first voice deploy runs from the old script's inode, so that deploy leaves `.env` alone and the next run adds the secret.

Observed on a real tailnet with LiveKit's binary on the host: `test:serve` on free ports, and a two-person call in Chrome with signalling through Serve and audio over `tailscale0`. Those two machines had a direct route. Observed from outside on a real VM: the Docker sidecar's `serve.json` 8443 entry answering, and `/api/info` reporting voice.
